- 标题：ANP 零知识认证 Profile
- 状态：提案 / 供社区讨论；非已发布规范
- 版本：0.1
- 语言：中文
- 英文镜像：[ANP Zero-Knowledge Authentication Profile (Proposal)](../../proposals/anp-zk-login-proposal.md)
- 适用范围：本提案适用于智能体与依赖方之间的请求认证，作为 [ANP-02](../../02-anp-did-authentication-protocol-specification.md) DID 签名流程之外的一种**可选**替代。

> **这是提案，不是规范。** 它提议为 ANP 协议集新增一个可选 Profile，不修改任何已发布文档。按 [CONTRIBUTING](../../CONTRIBUTING.cn.md)，它应当先经 GitHub Issue 与 Discord 讨论，之后再有任何将其晋升为已发布文档的 PR。下文的小节编号、标识符与错误码映射均为提案内容，可能在评审中变更。

> **为什么用独立 Profile 而不是改 ANP-02。** ANP-02 §3.2.1 第 4 步（L110）与 §3.2.2 第 4 步（L163）已把算法与密钥表示交由所选验证方法类型决定，附录 D（L503）也已预见其他方法"通过各自的解析与验证规则提供身份与认证密钥材料"。本提案是在既有 Profile 之外**新增**一个 Profile，而不是扩展 ANP-02 本身。

## 1. 摘要

ANP-02 通过 DID 签名的 HTTP 报文认证请求，这必然披露调用方的 `keyid`——一个完整的 DID URL（ANP-02 L82）。因此任何依赖方、以及任何观察到该请求的一方，都能得知是哪个 Agent DID 在调用，并可把该 DID 跨服务关联起来。

本提案定义 `anp.auth.zklogin.v1`：一个**可选启用**的认证 Profile。调用方以零知识方式证明自己持有某个被某个成员集合接纳的凭证，而**不传输 DID、公钥或任何跨服务稳定的标识**。启用该 Profile 的依赖方只会得到一个**按服务区分的假名**。

本 Profile 刻意做成纯增量：

- 复用 ANP-02 的线上载体（`Signature-Input` 选项、`Content-Digest`、401 挑战、§4 的 JSON 承载），不另立传输方式。
- 未实现它的依赖方不受影响；未实现它的客户端继续使用 DID 签名认证。
- ANP-01 至 ANP-10 均无改动。

### 1.1 本提案不做的事

- 不隐藏"该请求由零知识证明完成认证"这一事实，也不隐藏网络层元数据（来源地址、时序、请求大小）。
- 不使智能体对以其**其他方式**（支付、Handle、消息投递）识别自己的服务不可关联。见 §10。
- 不定义成员集合如何治理。准入策略属于集合签发方。见 §8。

## 2. 约定

本文中的 MUST、MUST NOT、REQUIRED、SHALL、SHALL NOT、SHOULD、SHOULD NOT、RECOMMENDED、MAY、OPTIONAL 按 BCP 14 解释。

§6.4 关系式所用记号：

| 记号 | 含义 |
|---|---|
| `sk` / `pk` | ZK 曲线的证明私钥及其对应公钥（§4） |
| `H_dom(tag, …)` | 取自陈述声明的哈希族、以 `tag` 做域分隔的哈希（§6.1） |
| `salt` | 注册时选定的每凭证随机值（§8） |
| `attrs` | 注册时承诺的已披露属性集；可为空 |
| `L`、`root`、`index`、`path` | 成员集合的叶子、其 Merkle 根、叶子下标、Merkle 路径 |
| `V` | 受众值，由客户端从所连接的 origin 推导（§6.5） |
| `baseHash` | 对该请求的 RFC 9421 签名基做 `SHA-256`（§6.6） |
| `h` | 按服务区分的假名（§6.4 第 3 条） |
| `sk_s` / `pk_s` | 会话私钥及其公钥；访问令牌绑定 `pk_s`（§6.8） |

## 3. 设计目标与非目标

**目标。**（a）线上不出现 DID、公钥或稳定标识。（b）完整的请求绑定：一个证明只对某一方法、目标 URI、authority、报文体与新鲜度窗口有效。（c）对已发布的 ANP 文档零改动。（d）后端无关：依赖方只要登记了某个证明系统的验证密钥就接受该系统的证明（§7）。（e）假名按服务稳定，使依赖方能够限流、封禁并维持会话。

**非目标。** 隐藏网络元数据；对串通的依赖方之间做到全局不可关联；定义成员集合的治理；在依赖方需要按 DID 寻址调用方的场合取代基于 DID 的认证。

## 4. 两层身份

朴素做法是直接证明 DID 私钥的成员资格。这会引入非原生域运算——在 BN254 电路里做 Ed25519 与 secp256k1 的标量乘——其约束数比原生运算大约高一个数量级。因此本 Profile 把两种角色分开：

1. **DID 私钥**只在**注册**时使用一次以授权准入（§8）。它从不用于登录，也从不出现在线上。
2. **证明私钥 `sk`** 是 ZK 电路自身曲线上的密钥。所有登录证明都用 `sk`。

成员叶子只承诺 `pk` 与 `attrs`（§6.4 第 2 条）。因此依赖方无法从它收到的任何内容中还原注册 DID，DID 的方法规则（ANP-03 / [附录 B](../../appendix-b-compatibility-with-native-did-web.md)）只约束注册环节。

实现 MUST 为注册与证明使用不同的密钥。把 DID 私钥复用为 `sk` 不影响正确性，但一旦该密钥作为 DID 文档的一部分被公开，目标（a）即告失效。

## 5. 可选启用与发现

依赖方通过声明本 Profile 来启用它。定义两种渠道，依赖方可只用其一或两者并用。

1. **能力声明。** 依赖方在其声明支持的 Profile 列表中列入 `anp.auth.zklogin.v1`，并附验证密钥引用（§7.3）。已发布智能体描述或服务描述的实现沿用该渠道。
2. **挑战。** 依赖方若希望以证明认证某请求，则返回 `401 Unauthorized` 并附加挑战，方式照 ANP-02 L238–L244：

```http
WWW-Authenticate: ANPZK realm="api.example.com", profile="anp.auth.zklogin.v1",
  statement="anp.auth.zklogin.v1/<params-hash>", vk="https://api.example.com/zk/vk.json",
  nonce="xyz987", error="invalid_signature"
Accept-Signature: sig1=("@method" "@target-uri" "@authority" "content-digest")
```

**回退规则。**

- 支持本 Profile 的客户端收到点名 `anp.auth.zklogin.v1` 的挑战时，MUST 以证明请求作答，而不是 DID 签名请求。
- 不支持它的客户端 MUST 忽略该挑战并使用 ANP-02 认证；依赖方随后可按自身策略接受或拒绝该尝试（见下文的 `required`）。
- 把某操作声明为 **ZK 必需**的依赖方（例如仅为此操作声明本 Profile）MUST NOT 接受该操作的 DID 签名登录。客户端 MUST NOT 把此类拒绝当作改用 DID 签名重试的理由。
- 依赖方 MUST NOT 把 ZK 必需的操作静默降级为 ANP-02 认证。这与多版本消息 Profile 已采用的"不得静默降级"纪律一致。

## 6. 证明陈述

### 6.1 陈述标识与参数

陈述标识同时包含**关系式**与**一切一旦改变即改变证明含义的参数**。它是一个形如下式的字符串：

```text
statementId := "anp.auth.zklogin.v1" "/" paramsHash
paramsHash := base64url(SHA-256(canonical-JSON(params)))
params     := { "curve": …, "leafHash": …, "merkleArity": …, "encoding": …, "relationRev": … }
```

`canonical-JSON` 即 ANP 其他地方已在用的 JCS 规范化。两条规则：

- 证明方与验证方 MUST 就 `statementId` 精确一致；不一致即属于不同的 Profile 实例，MUST 拒绝。
- 实现 MUST NOT 在保持 `statementId` 不变的前提下改动 `params` 的任一成员。特别是哈希族 MUST 由 `params.leafHash` 固定，不得按部署自选。

原因是假名 `h` 由见证值派生，并被依赖方当作长期句柄使用（§9）。若哈希族在标识不变的情况下发生改变，同一智能体在同一服务上会**静默变成另一个假名**。把参数绑进标识，使任何此类改动成为显式、需协商的断点。

### 6.2 公开输入

| 输入 | 来源 | 绑定的是 |
|---|---|---|
| `root` | 成员集合的 epoch 状态（§8） | 调用方属于哪个集合 |
| `V` | 由客户端从所连 origin 推导（§6.5） | 受众 |
| `baseHash` | 验证方可从真实请求重算（§6.6） | 精确的那个请求 |
| `h` | 假名，按构造即公开 | 调用方的按服务句柄 |
| `pk_s` | 由客户端声明；签发的令牌绑定它（§6.8） | 会话钥 |
| `bindTag` | 公开输出（§6.4 第 7 条） | 把以上各项系在一起 |
| `nonce`、`created`、`expires` | ANP-02 的新鲜度参数 | 新鲜度 |

### 6.3 见证（永不传输）

`sk`、`sk_s`、`salt`、`attrs`、`index`，以及从 `L` 到 `root` 的 Merkle `path`。

### 6.4 关系式

仅当存在满足下列全部条件的见证值时，证明才有效：

1. **密钥知识。** `pk = derive(sk)`，`derive` 由陈述声明。
2. **成员资格。** `L = H_dom(TAG_LEAF, pk, salt, H_dom(TAG_ATTR, attrs))`，且 `L` 是沿 `path` 位于 `root` 之下第 `index` 位的叶子。
3. **假名正确性。** `h = H_dom(TAG_PSEUDONYM, sk, V, statementId)`。
4. **披露一致性。** 已披露的 `attrs`（若本 Profile 与选择性披露并用，§6.7）与第 2 条所承诺的 `attrs` 完全一致。
5. **会话钥知识。** `pk_s = derive(sk_s)`，即调用方证明自己持有 `pk_s` 所指名的会话钥。签发的令牌绑定 `pk_s`（§6.8），因此这一条不可省：没有它，任何调用方都能指名任何 `pk_s`。
6. **请求绑定。** `baseHash` 属于陈述的公开输入，因此为某一请求生成的证明无法对另一请求的公开输入通过验证。
7. **联合绑定（公开输出）。** 关系式发布
   `bindTag = H_dom(TAG_BIND, h, baseHash, V, root, nonce)`。
   验证方 MUST 以自身视角的 `h`、`baseHash`、`V`、`root`、`nonce` 重算 `bindTag`，不一致即 MUST 拒绝。由于第 7 条在电路内把六个值约束在一起，其中任何一个都无法在证明之后被替换。

### 6.5 `V` 由客户端推导

客户端 MUST 从它实际连接的 origin——真实请求的 scheme 与 authority——推导 `V`，且 MUST NOT 接受依赖方给出的 `V`。

**理由。** 若由依赖方选择 `V`，两个串通的依赖方即可约定同一个 `V`，在两边观察到同一个 `h`，从而把调用方跨服务关联起来。这将直接摧毁本 Profile 的目的。从所连 origin 客户端侧推导 `V`，使假名依赖一个依赖方无法施加影响的值。这与 ANP-02 对 `@target-uri` 已采用的纪律相同：验证方应当"从真实请求推导"该值，而非仅凭调用方给出的目标 URI。

验证方 MUST 独立地为它收到的请求计算期望的 `V`，并 MUST 拒绝 `V` 不匹配的证明。

### 6.6 验证方检查

除验证证明本身之外，验证方 MUST：

1. 从真实请求（方法、目标 URI、authority、`Content-Digest` 以及被覆盖的选项）重算 `baseHash`，不一致即拒绝。不得信任客户端给出的 `baseHash`。
2. 按 §6.5 重算 `V`，不一致即拒绝。
3. 采用与 ANP-02 §3.2.1 第 7 步（L141）相同的新鲜度窗口，其中 `expires` 按 SHOULD 处理（ANP-02 L85）：缺失时仅以 `created` 单边限窗。
4. 维护重放缓存。匿名模式下，ANP-02 的 `(keyid, nonce)` 缓存（ANP-02 L144、L437）变为 `(h, nonce)`。一个 nonce 对每个 `h` MUST 只能使用一次。
5. 对其假名策略作用于 `h`：限流、封禁、会话绑定（§9）。

### 6.7 选择性披露（可选）

Profile 实例 MAY 声明一个披露集合。声明后，关系式在**不**暴露其余部分的前提下，额外证明已披露属性等于所承诺者（第 4 条）。不需要属性的依赖方使用空 `attrs`，这也是 RECOMMENDED 的默认。

### 6.8 后续请求与令牌绑定

一个证明只认证一次请求。至于之后怎么办，ANP-02 已有安排：服务端通过 `Authentication-Info` 返回访问令牌（ANP-02 L197），其 §3.2.3 第 3 项（L205–L215）预留了一种 **sender-constrained** 令牌，把令牌绑在客户端持有的密钥上——同时明确声明该档尚未定义。

本 Profile 用 §6.4 第 5 条的会话钥 `pk_s` 填上这一预留格位。令牌携带一条指名为 `pk_s` 的确认声明（confirmation claim），因此被窃的令牌离开 `sk_s` 即无用。会话上的后续请求出示令牌并证明持有 `sk_s`，**不再**携带新的证明。依赖方：

- MUST 把它签发的令牌绑定到该证明所声明的 `pk_s`；
- MUST NOT 对已建立的会话要求每个请求都附一份新的零知识证明。

由于令牌类型不是 `Bearer`，按 ANP-02 L225，客户端 MUST 依本规范发送它：令牌以对 `sk_s` 的持有证明出示，而不是当作持有者凭证。不需要 sender-constrained 令牌的部署 MAY 按 ANP-02 允许的方式（L215）签发 `Bearer` 令牌，但 SHOULD 优先选择绑定，因为 `pk_s` 本就已在手，不额外付出代价。

## 7. 证明系统兼容

本 Profile 不强制某一证明系统。它接受依赖方已为其登记验证密钥的任何系统，由三段式描述符刻画。

### 7.1 描述符三元组

```text
(scheme, statementId, vkHash)
```

- `scheme`——证明系统，例如 `groth16`、`plonk`、`halo2`、`stark`。
- `statementId`——§6.1，内嵌曲线与哈希参数。
- `vkHash`——`sha256-<base64url(SHA-256(canonical-JSON(verificationKey)))>`，使依赖方能按哈希而非按 URL 钉住某证明系统的密钥材料。

三者 MUST 全部命中一条已登记条目，证明才会被接受。其中任一改变都会得到不同的验证密钥，因而也是不同的 Profile 实例。

该三元组与 EIP-8288 所用的依赖框架 `(scheme, data_hash, verification_key_hash)` 形状相同；见 §13。

### 7.2 证明信封

当证明经 JSON 承载（§7.4）传输时，它是一个对象：

```json
{
  "scheme": "groth16",
  "statementId": "anp.auth.zklogin.v1/<params-hash>",
  "vkHash": "sha256-<base64url>",
  "proof": "<opaque, encoding fixed by scheme>"
}
```

`proof` 对本 Profile 不透明。其编码由 `scheme` 固定，且 MUST NOT 在同一 `statementId` 内变化。

### 7.3 验证密钥引用

依赖方 MUST 公布客户端获取其所接受验证密钥的方式，并 MUST 按 `vkHash` 钉住它们。依赖方 MAY 从稳定的 HTTPS URL 提供，并 MAY 在挑战中声明该 URL（§5 的 `vk=`）。实现 MUST NOT 接受客户端提供的验证密钥。

### 7.4 可移植接口

合规的证明后端恰好暴露两个操作：由陈述与见证生成证明，以及以陈述验证证明。本 Profile 的贡献是**可移植的陈述**——§6.2 至 §6.4——而非后端。实现了该陈述的后端可以互换而不改变线上格式，因为线上只携带描述符三元组与不透明的证明。

### 7.5 聚合（信息性）

未来修订版可能允许一个聚合证明覆盖多个陈述（例如成员资格加属性披露）。本提案不定义它，只在信封的可扩展性上为它留位。

## 8. 注册

注册**不属于线上协议范畴**，由成员集合的签发方治理。本节只给出依赖方所依赖的约束。

1. 注册 MUST 由一个已认证的身份授权——RECOMMENDED：一次 ANP-02 DID 签名请求，DID 私钥正是在此处使用其唯一一次（§4）。随后待注册智能体提交 `pk` 与 `attrs`。
2. 签发方以新生成的 `salt` 计算 `L = H_dom(TAG_LEAF, pk, salt, H_dom(TAG_ATTR, attrs))`，把 `L` 插入集合，并把 `(index, path, salt)` 返回给智能体。
3. `salt` MUST 不可预测，且 MUST NOT 在凭证之间复用。没有它，低熵的 `attrs` 可从 `L` 被猜出。
4. 签发方执行其自身的准入策略，包括在策略要求时做到"每主体一凭证"。它为此保留的记录是签发方本地的，不上线。

成员集合的构造方式——准入式集合、签发方为根的集合及其取舍——属于本 Profile 不予标准化的治理话题（§14 第 6 项）。

## 9. 依赖方的账号模型与留痕

### 9.1 假名就是账号

`h` 是依赖方能看到的唯一长期标识符，而且是确定性的：它只取决于 `sk`、`V` 与 `statementId`，别无其他（§6.4 第 3 条）。对"同一智能体访问同一服务"而言，三者都不变，因此每次登录都得到**同一个** `h`。假名**就是**账号：

| 情形 | `h` 是否相同 | 依赖方看到的是 |
|---|---|---|
| 同一智能体、同一服务、多次登录 | 相同 | 一个账号 |
| 同一智能体、不同服务 | 不同 | 两个不可关联的账号 |
| 同一智能体、同一服务、换了凭证 | 不同 | 另一个账号（§9.3 第 2 项） |

本 Profile 隐藏的是**跨服务**的关联性，而不是站内的一致性。站内一致性正是限流、封禁、信誉得以成立的前提；代价是依赖方能够对某位来访者做长期画像，§10 要求它披露这一点。

`h` MUST 被当作不透明句柄：

- 对给定的 (`sk`, `V`, `statementId`) 它是稳定的，因此依赖方可以按它限流、封禁并维持会话。
- 它与该智能体的 DID 不可关联，与该智能体在其他服务上呈现的假名也不可关联——前提是 `V` 按服务各不相同（§6.5）。
- 同一智能体只有在使用不同凭证时，才可能对同一服务随时间呈现不同假名；本 Profile 不定义凭证更新。

对某操作声明为 ZK 必需的依赖方，MUST NOT 把"泄露 DID 或其他标识"作为该操作 ZK 登录的条件。当它确实需要按 DID 寻址该智能体时，MAY 另设一条明确标注的路径（§9.3 第 1 项，可寻址模式）。

### 9.2 依赖方存什么

匿名模式下不存在 `h → DID` 的映射，依赖方 MUST NOT 试图构造一条。它对某位来访者的记录只以 `h` 为键：

| 字段 | 用途 |
|---|---|
| `h`（主键） | 依赖方对该来访者的全部认知 |
| `pk_s` | 会话钥；访问令牌的确认声明绑的就是它（§6.8） |
| `disclosed` | 本次登录披露的属性子集 |
| `escrow` | 保险箱密文，`mode` 为 `escrow` 时（§10） |
| `mode` / `statementId` / `scheme` / `vkHash` / `epoch` | 本次证明的出处，审计与排障必需 |
| `created` / `expires` / `nonce` | 与 ANP-02 的新鲜度参数对齐 |
| 结论 | 通过或拒绝 |

同时担任成员集合签发方的依赖方，还需保留集合的 `setId`、`epoch` 与当前根，**以及历史根**——§6.6 的宽限窗口与日后的审计都需要它们。

### 9.3 依赖方必须接受的后果

以下是设计的性质而非缺陷，依赖方 MUST 在其描述符（§5）中披露：

1. **无法主动联系。** `h` 不是可路由地址。必须事后按 DID 联系该智能体的依赖方无法从 `h` 做到；这正是可选的可寻址模式存在的理由（§12）。
2. **没有恢复路径。** 智能体丢失 `sk`，或以不同凭证重新注册，得到的 `h` 即不同，依赖方看到的就是另一个账号。本 Profile 不定义任何恢复、合并或账号关联路径。
3. **封禁受制于准入。** 依赖方封的是 `h`；智能体以新凭证重新注册就得到新的 `h`。因此封禁只在注册渠道能够拒绝其重新准入的范围内有效（§8）。封禁 MUST NOT 被表述为身份层面的保证。
4. **风控手段减少。** 证明不携带设备指纹、账号关联或行为信号。依赖方的替代品只有速率、行为、可选披露的属性与托管路径，别无其他。传统的账号关联与异常登录检测基本不适用。

### 9.4 证明的留痕

证明是**一次性的**。它被一个 `baseHash`、一个 `h`、一个 `nonce` 与一个新鲜度窗口绑在唯一一次请求上（§6.4、§6.6）；窗口一过、nonce 一消耗，再验它就什么都证明不了。因此认证的推进方式与 ANP-02 相同：验证证明、签发会话或访问令牌，后续请求用令牌而不再用新的证明。

所以留痕与否**不是为了将来再验**，而是为了第三方日后能否**复核那次准入决策**。留痕与 §10 的去匿名化档位相互独立——部署可以"匿名档但留证明"，也可以"托管档但丢弃证明"。本 Profile 定义两种模型：

- **模型 A（RECOMMENDED 默认）。** 存公开输入、结论与时间，**丢弃证明**。日后的审计只能确认依赖方当时记录了一次通过的验证。
- **模型 B。** 存证明，或至少存 `hash(证明)`。由于证明是 NIZK、公开可验证，持有公开输入与证明的第三方无需信任依赖方即可重算该决策。

依赖方 MUST 声明自己采用哪种模型，且 MUST NOT 超出该模型所需保留证明。注意：证明不是标识符，不提供任何归因——它天生不指名，因此模型 B 的证据价值仅限于准入决策可复核。部署若提供归因，只能来自托管路径（§10）。

### 9.5 限流与封禁

限流按 `h` 施加。依赖方 MUST NOT 把 DID 或其他稳定标识作为准入的代价，也 MUST NOT 退回到某种共享标识以跨服务执行封禁：跨服务封禁是刻意做不到的，因为 `h` 按服务各不相同。

## 10. 隐私考量

**受保护的。** 调用方的 DID、公钥与注册属性不被披露。只要各服务从各自 origin 推导 `V` 且互不串通，跨服务关联即被阻止。

**不受保护的。** 网络元数据（来源地址、时序、请求大小、TLS SNI）不变。依赖方会得知该请求使用了 ZK 登录。共享 `V` 的两个依赖方——例如一方是另一方的前台，或客户端被胁迫复用 `V`——可以相互关联。实现 SHOULD 说明 `V` 是按 origin 推导的，且 MUST NOT 跨 origin 复用。

**审计档（提案，未定）。** 部署方可能希望为滥用处置保留一条去匿名化路径。提案两种档位：**匿名档**，不存在此类路径；**托管档**，凭证携带一份只有指定审计方能读的托管密文。默认档是待定问题（§14 第 2 项）。依赖方 MUST 披露它采用哪一档。档位由客户端选择并作为公开输入携带，因此依赖方可以选择接受哪些档位，但不能强迫智能体交出托管密文。

这条去匿名化的轴与 §9.4 的留痕模型**相互独立**。部署可以是"匿名档但留证明"，也可以是"托管档但丢弃证明"；两者回答的是不同的问题（"这次登录能否被归因到一个真实身份"与"第三方能否复核那次准入决策"）。实现 MUST NOT 把二者混为一谈。

## 11. 安全考量

- **可靠性（soundness）。** 安全性建立在证明系统的可靠性与陈述的约束之上。依赖方 MUST 拒绝其未登记 `scheme` 的证明（错误映射见 §12）。
- **可信设置。** 需要可信设置的证明系统（例如 Groth16）继承其假设。无法接受该假设的依赖方应改为登记透明设置的证明系统；本 Profile 不强制选择（§7）。
- **重放。** 由新鲜度窗口与 `(h, nonce)` 重放缓存处理（§6.6）。
- **成员集合新鲜度。** `root` 随集合变动而变。验证方 MUST 公布它正在校验的 epoch，并 MUST 定义一个宽限窗口：在此窗口内，针对紧邻的前一个 `root` 的证明仍被接受，以免一次注册或移除使在途请求失效。窗口长度属策略选择。
- **证明成本。** 证明生成刻意放在客户端。依赖方 MUST NOT 对非其发起的请求要求在自己的基础设施上生成证明。
- **拒绝服务。** 验证证明比验证签名更昂贵。依赖方 SHOULD 对任何未认证端点施加与其既有做法一致的请求级准入控制。

## 12. 对 ANP-02 的偏离

本 Profile 对 ANP-02 恰好做出一处刻意偏离，也正是匿名模式无法表达为普通 ANP-02 请求的原因：

**`keyid`。** ANP-02 L82 要求 `keyid` 是完整的 DID URL，附录 B L487 再次重申。匿名模式下没有 DID 可指。因此本 Profile 允许 `keyid` 或者省略、身份材料改由证明信封携带，或者置为假名 `h`——后者不是 DID URL。

依赖方 MUST 处理两个后果：

1. ANP-02 以 `(keyid, nonce)` 为键的重放缓存（L144、L437）变为 `(h, nonce)`。
2. 任何"从 `keyid` 解析密钥"的 ANP-02 条款都不适用；验证密钥按 §7.3 获取。

**可寻址模式（可选）。** 必须事后按 DID 寻址该智能体的依赖方无法从 `h` 做到。此类部署 MAY 要求一份额外的、明确标注的证明，把凭证与某个 DID 或 Handle 绑定，且只向该依赖方披露。本提案不定义该证明，它被列为待定问题（§14）。依赖方 MUST NOT 静默要求它。

**错误映射。** 本 Profile 按下列方式复用 ANP-02 的错误词表（L252–L260）：

| 情形 | 错误值 |
|---|---|
| 信封畸形、字段缺失、`scheme` 未知 | `invalid_request` |
| nonce 被复用或未知 | `invalid_nonce` |
| 时间戳越窗 | `invalid_timestamp` |
| 证明未通过验证 | `invalid_signature` |
| `statementId` 或 `vkHash` 未登记 | `invalid_verification_method` |
| `Content-Digest` 不匹配 | `invalid_content_digest` |
| 假名被策略拒绝 | `forbidden_did` |
| Access Token 绑定失败 | `invalid_access_token` |

`invalid_did`（L255）在匿名模式下无意义，不予使用。把 `forbidden_did` 复用为假名策略错误是一种命名上的妥协；是否新增一个专用值属待定问题（§14）。

## 13. 与既有文档的关系

| 文档 | 关系 |
|---|---|
| [ANP-02](../../02-anp-did-authentication-protocol-specification.md) | 本 Profile 所依附的载体。§3 的头字段集合、`Content-Digest`、新鲜度、401 挑战、§4 的 JSON 承载、错误词表，以及预留的 sender-constrained 令牌格位（§6.8）全部复用。注册使用 ANP-02 的 DID 签名流程（§8）。 |
| [ANP-03](../../03-did-wba-method-design-specification.md) | 只治理注册身份。其 L205 说明"其他标准中定义但此处未列出的字段也可被选择性支持"，本 Profile 的新增内容正是在该条款下作为可选、非破坏性扩展。 |
| [ANP-06](../../06-anp-agent-communication-meta-protocol-specification.md) | 无改动。依赖方 MAY 通过它用于其他 Profile 的同一能力机制声明本 Profile。 |
| ANP 消息 P1–P9 | 无改动，也不是依赖。认证与消息是彼此独立的关注点，如 ANP-02 §1 所述。 |
| [ANP-10](../../application/10-anp-agent-payment-protocol-specification.md) | 无改动。其"支持选择性披露、最小化不必要的信息泄露"原则是本 Profile 的一个动机，但两者相互独立。 |

**与 EIP-8288 的同构（信息性）。** §7.1 的描述符三元组——`(scheme, statementId, vkHash)`——与 EIP-8288 的 `(scheme, data_hash, verification_key_hash)` 形状相同。二者从不同方向抵达同一结构：EIP-8288 通过指明验证依赖来刻画一个被签名物，本 Profile 通过指明证明的验证依赖来刻画它。若社区认为这一平行关系有用，未来修订版可考虑对齐字段名。

## 14. 待定问题

1. **能否进一步削弱这处偏离。** §12 去掉了 `keyid`。一种保留 DID 形状 `keyid` 的"可寻址模式"可把偏离降到零，代价是披露一个 DID。对同时需要按 DID 寻址智能体的依赖方，哪个应作默认？
2. **审计档默认值。** 默认应是 `anonymous`（无去匿名化路径）还是 `escrow`（指定审计方可开启凭证）？§10 留待决定，因为它属治理与责任选择，而非密码学选择。
3. **错误词表。** 把 `forbidden_did` 复用于假名策略拒绝是否可接受，还是 ANP-02 的错误集应新增一个专用值？
4. **归属。** 它应作为 ANP-02 旁的认证 Profile（如本提案所设）、作为 `application/` 下的带编号文档、还是作为核心集之外的独立扩展？本提案假定为第一种。
5. **注册渠道。** ANP-02 DID 签名注册（§8）是否是正确的 RECOMMENDED 渠道，还是注册从一开始就应当与方法无关？
6. **成员集合治理。** 本提案任何部分都不定义谁可签发凭证、集合如何联邦。若社区需要标准的集合接口，应另立文档。
